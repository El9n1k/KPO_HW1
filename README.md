## Отчет  
*Выполнил Андреев Никита Алексеевич*

Консольное приложение на C# (.NET 10) для учёта техники и вещей парка «ВышКат».
Техника попадает на баланс только после техосмотра, каждой единице присваивается инвентарный номер,
доступны отчёты по энергопотреблению, по технике для новичков и по всему имуществу.

## Запуск

```zsh
dotnet run      # запуск приложения из HW1/HW1/
dotnet test     # запуск юнит-тестов из HW1.Tests/
```
Для запуска демонстрации работы приложения введите команду: demo.

## Логика решений

**Доменная модель построена на интерфейсах, c иерархией вещей (наследовании).**

- IEntity имеет свойства Id, Name, Simplicity. Это всё, что можно поставить на баланс (и транспорт, и вещи). Свойство
Simplicity есть у каждой сущности, так как в моем понимании новичком может быть как клиент, так и сотрудник. *Никто же
не доверит новенькому сотруднику самую сложную зарядную станцию)*.
- IMovable : IEntity добавляет MaxSpeed. Это признак транспорта.
- IEnergyConsumer : IEntity добавляет DayConsumption (кВт/ч в сутки).
- Конкретные классы просто набирают нужные роли (множественно наследуют необходимые интерфейсы): Bike, Scooter это 
IMovable; EBike это IMovable + IEnergyConsumer; Helmet это IEntity; EnergyStation это IEnergyConsumer.

**Сервисы:**

- Park — Основная логика работы с парком: прием и удаление (*Удаление реализовано дополнительно, явных требований 
в задании к неему не предъявлялось*). Сначала спрашивает IServiceCenter.Inspect, и только при true кладёт 
сущность в IRepository. ID сущности выдаёт репозиторий, поэтому отклонённая техника ID не «съедает».
- ServiceCenter — техосмотр: простота в диапазоне 1–10; для IEnergyConsumer расход от 0 до 1 000 000 
(*Поставил лишь для того, чтобы показать возможность фильтрации входных данных на соответствие реальности)*); для IMovable скорость от 0 до 40.
- Repository — хранилище в памяти. Номера растут монотонно и **не переиспользуются** после удаления.
- IReport — общий интерфейс для отчетов с возможностью добавления новых отчетов. 
Сейчас реализованы три отчета: EnergyReport, NewbieReport, EntitiesReport.
Все они получают данные из IRepository.
- InewbieRules — правило «для новичков»: простота ≥ 6. NewbieReport дополнительно оставляет только IMovable, 
потому что по заданию список именно **прокатной техники**.

**Консольный слой (UI):**  
ConsoleMenu главный класс интерфейса. Он владеет циклом ввода-вывода (его вызывает Program.cs), разбирает команды
и маршрутизирует их дальше. При этом бизнес-логикой данный класс не занимается.
ConsoleMenu также не знает конкретных типов сущностей и отчётов. Он получает из DI список IEntityParser
и список IReport и выбирает нужный по строке (EntityType / Type). Каждый ***Parser читает поля одного типа
через ConsoleInput (общая валидация ввода).

**Кто что делает:**
- ConsoleMenu, ***Parser, ConsoleInput, DemoRunner (слой UI): ввод, вывод, выбор команды.
- Park (прикладной слой): сценарий «принять или удалить». Сам правил не содержит, а вызывает техосмотр и репозиторий.
- ServiceCenter, InewbieRules, отчёты (бизнес-правила): что можно принять, что подходит новичку, как считается энергия.
- Repository (хранение).
- Models (сущности и роли).

Зависимости идут в одну сторону: UI -> Services -> Models. Models ни от чего не зависят, 
Services ничего не знают о консоли.

## Применение SOLID
- **S (single responsibility).** Приём решает ServiceCenter, хранение и номера — Repository, 
добавление и удаление — Park, правило новичка — InewbieRules, форматирование — отчёты, ввод — 
парсеры и ConsoleInput. Каждый ответственнен строго за один функционал. God-класса, который одновременно содержал бы
бизнес-логику, модели и т. д. - **НЕТ**.
- **O (open/closed).** Новый вид сущности добавляется классом (наследующим уже созданные интерфейсы: IEntity,
IMovable и т. д.) + парсером для этого класса (наследующим также общий интерфейс парсеров: IEntityParser) + 
одной строкой регистрации в DI-контейнере в Program.cs. 
Новый отчёт — классом, наследующим интерфейс IReport + регистрацией. 
ConsoleMenu, Park, Repository при этом не меняются, то есть бизнес-логика, UI, а также модели не меняются. 
- **L (Barbara Liskov principle).** Любая реализация IEntity, IServiceCenter, IRepository, IReport взаимозаменяема:
код работает через интерфейсы и не проверяет конкретные классы. Тесты подставляют fake-реализации без изменения кода.
- **I (interface segregation).** Скорость и энергия вынесены в отдельные интерфейсы IMovable и IEnergyConsumer. 
Шлему не нужна скорость, обычному самокату не нужен расход энергии. EnergyReport работает только с IEnergyConsumer. 
IServiceCenter содержит один метод Inspect. Park получает ровно то, что ему нужно, и ничего лишнего. IInewbieRules 
тоже содержит один метод, IsForNewbie. NewbieReport зависит только от него, поэтому в тестах правило заменяется 
заглушкой StubNewbieRules из одной строки.
- **D (dependency inversion).** Models ни от чего не зависят. Services зависят только от модели, 
но ничего не знают о UI. DIP - выполняется. Park, отчёты и ConsoleMenu получают зависимости через конструктор 
в виде интерфейсов. Сборка графа находится в одном месте, 
в Program.cs (DI-контейнер Microsoft.Extensions.DependencyInjection).

## Ответы на обязательные вопросы

### 1. Какой принцип применён наиболее явно

**Открытость/закрытость (O), в связке с DIP.** Показательные места:
- IEntityParser и ConsoleMenu: меню перебирает все зарегистрированные парсеры, а не знает о конкретных типах.
Добавление типа не требует правки меню.
- IReport и ConsoleMenu.PrintReport: то же самое для отчётов.
- ServiceCenter и EnergyReport проверяют роли (IMovable, IEnergyConsumer), а не конкретные классы, 
поэтому новый транспорт с новой ролью подхватывается автоматически.
- IInewbieRules специально вынесены в интерфейс, чтобы при расширении программы была возможность добавить функции
с более специфичной проверкой пригодности для каждого вида транспорта.
- IRepository единый интерфейс, который я под капотом реализовал через список, однако при расширении может понадобиться
хранить данные, к примеру, через dictionary и т. д.. С текущим интерфейсом это легко реализовать.

### 2. Какой принцип сознательно ограничен

**Open/closed внутри ServiceCenter.** Правила техосмотра записаны цепочкой if в одном методе Inspect,
а пороги (10, 40, 1 000 000) вшиты константами. Если понадобится, например, отдельный предел скорости для самокатов,
придётся править этот метод. Почему это приемлемо: правил всего три, они короткие и логически связаны, а выделение
IInspectionRule + коллекции правил для трёх проверок было бы «мертвым» SOLID/overengineering.   
**Single responsibility в отчетах и ConsoleMenu.** Разбивать отчеты отедельно на подсчет данных и формирование самого
отчета не вижу смысла, так как это overengineering. В ConsoleMenu несмотря на то, что класс выполняет много действий, 
это происходит только по одной причине: изменились команды или тексты диалога. То есть меню это тонкий маршрутизатор: 
оно знает кого позвать, но не как работает.

*Дополнительно, компромисс:*  
ConsoleMenu зависит от конкретных Park и DemoRunner, у которых нет интерфейсов. В проекте единственная реализация 
каждого, и интерфейс «ради интерфейса» не даёт выгоды, а наоборот приводит к «мертвому» SOLID/overengineering. Подмена на уровне тестов делается через IServiceCenter,
IRepository, IReport, IEntityParser.

### 3. Ничего не должно ломаться при расширении

- **Новый вид транспорта** (например, Skateboard : IMovable). Нужно: класс, парсер
(SkateboardParser : IEntityParser), строка AddSingleton<IEntityParser, SkateboardParser>() в Program.cs.
**Не ломается и не меняется:** Park, Repository, ServiceCenter, все отчёты, ConsoleMenu.
Транспорт автоматически проверяется на скорость и попадает в «новичковый» отчёт.
Единственное ограничение: общий предел скорости 40 для всех IMovable (см. вопрос 2).
- **Электро-транспорт** получается добавлением IEnergyConsumer к классу;
он автоматически попадает в EnergyReport и проверку расхода в ServiceCenter.
- **Сотрудник.** Сотрудники не ставятся на баланс. При желании расширять приложение и ставить сотрудников на баланс 
это можно сделать созданием нового интерфейса-наследника от IEntity. Никакой уже написанный код менять не нужно.  
- **Склад запчастей.** Запчасть это новый класс IEntity (+ парсер + регистрация), а сам склад можно сделать как ещё
одну реализацию IRepository. Код Park и отчётов не меняется.
- **Новое правило для новичков** — другая реализация IInewbieRules, регистрируется вместо InewbieRules. 
NewbieReport не меняется.

### 4. Какие тесты фиксируют решения и как подменяется зависимость

**Техосмотр:**
- ServiceCenterTests проверяют сам ServiceCenter: допустимая сущность, отклонение по простоте, скорости и расходу.
- ParkTests.Add_ShouldReturnTrueIfServiceCenterAcceptsEntity и Add_ShouldReturnFalseIfServiceCenterRejectsEntity
подменяют IServiceCenter на fake (FakeServiceCenterTrue/False) и проверяют, что Park кладёт сущность
в репозиторий при решении «принять».
- ParkTests.Add_ShouldReturnFalseIfRealServiceCenterRejectsEntity берёт **те же значения**, но с настоящим
ServiceCenter, и получает отказ. Парой эти два теста доказывают, что решение принимает именно техосмотр.
- ParkTests.Add_ShouldCallServiceCenterInspect (spy) проверяет, что Park вообще обращается к техосмотру.
- ParkTests.Add_ShouldNotConsumeIdForRejectedEntity проверяет, что отклонённая техника не занимает инвентарный номер.
- ConsoleMenuTests.Add_WhenInjectedInspectionRejects_... и ..._Accepts_... показывают подмену на уровне всего
приложения: в контейнере настоящая регистрация заменяется fake-ом через services.Replace(...).

ParkTests и ConsoleMenuTest передают (подменяют) fake/mock/stub/(spy) через DI. (*Подробнее - ниже*)

**Правило «для новичков»:**
- InewbieRulesTests: граничные значения 7, 6 (подходит) и 5 (не подходит).
- NewbieReportTests: настоящее правило (простота 6 попадает, 5 нет; шлем и зарядная станция не попадают; 
электровелосипед попадает) и заглушка StubNewbieRules(true/false), подставленная вместо IInewbieRules:
«принимает всё» (всё равно отсекаются не-транспорт), «отклоняет всё» (пустой отчёт).

Остальные тесты: RepositoryTests (номера, удаление, отсутствие переиспользования), ReportTests (энергия, 
список имущества, количество единиц, пустой парк), ParserTests (поля, повторный запрос при неверном вводе,
точка/запятая), ConsoleMenuTests (команды, регистр, справка, quit, подмена парсеров и отчётов mock-ами).

**Как подменяется зависимость:** тест собирает свой ServiceCollection (DI), регистрирует в нём fake/stub/mock/(spy) и
получает Park/ConsoleMenu/отчёт из DI-контейнера.

Покрытие тестов: 82% *Проверял через:*
```zsh
dotnet test --collect:"XPlat Code Coverage"
```

### 5. Роль ИИ
При разработке архитектуры, а также написании кода самого проекта ИИ **НЕ** использовался. Созданием тестов 
(придумыванием сценариев, разработкой fake/mock/stub/(spy)) также занимался я лично. ИИ лишь помог быстро написать 
каждый из тестовых кейсов.

## Прочее
Придерживался **Microsoft .NET code style**.   
В тестах много повторяющихся фейковых классов так как каждому тесту удобен свой фейк. Сами фейки маленькие, 
поэтому не вижу смысла делать overengineering и объединять их как-либо.   
Нет IreportPrinter и IreportSaver так как создавать отдельные интерфейсы ради одной функции, на мой взгляд,
было бы тоже overengineering.
